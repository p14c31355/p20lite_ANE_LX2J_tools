# ANE-LX2J 自走記録 2026-10-02 (デバイス時間 22:00 まで)

## 体制

- **自走ランナー** `ane_night.sh` (バックグラウンド健全動作中):
  状態 (fastboot / adb / huawei-gadget / dark) を監視し、キューを消化する。
  - fastboot → キューの次のプローブを焼いて起動 (ハング型)→ watchdog の
    fastboot フォールバック (~4.5 分) を待って次へ。キューが空なら
    **ストック復元 → Android**。
  - adb の短い窓 (起動直後 ~10 秒) を捕まえたら `adb reboot bootloader`。
  - rescue → ログ (sudoers 未設定のため USB 抜き差しは実行不可)。
- ログ: `usb_runs/night_*.log` / USB イベント: `night_journal_*.log` /
  カメラ: `usb_runs/cam_*/` (プローブ生存中に 18 秒毎のスナップショット + 色分析)
- キュー `night_queue.txt`: **l1b → l1c → rch-hang → paint(ベースライン) →
  stepmarks2 → paint(マーク読み出し) → USBJOB**
  - l1b = L1 + abb ゲート / l1c = さらに DWC2 コア初期化
    (GUSBCFG.ForceDevMode + UTMI+8bit + コアソフトリセット + DCFG.DevSpd=HS)。
    旧 dwc_otg CIL (cil.c 1300-1420) の手順を一次ソースとして反映。
  - paint ベースライン = マーク未書き込み状態で描画チャネルだけを検証
    (帯 0 = 白のみ見えるはず)
  - stepmarks2 → paint = Fullerene がどこで死んだかの読み出し
- 原則: **プローブはハングで終える** (SMC ループは rescue に落ちて人が要る)。
- 稼働は 09:00 まで延長 (朝の押下でもパイプラインが自動で流れるように)。
- **朝の使い方**: `STOP_WHEN_QUEUE_EMPTY=1 bash ane_night.sh` で「キュー消化 →
  ストック復元 → 自動終了」。押下 (音量下+電源) の後に走らせれば、全プローブが
  自動で流れて最後は Android に戻る。

## parking からの解法試行 (10:13-10:15)

- 端末の usbfs ノードは root:plugdev + ACL で、このアカウントは plugdev 所属
  → **sudo なしで USB 操作が可能** (`tools/ane_usb_reset_user.py` /
  `ane_usb_config_dance.py`)。
- 試した: ①ポートリセット (USBDEVFS_RESET) → 再列挙したが構成は不変。
  ②SET_CONFIGURATION(0)→(1) ダンス → 変化なし。
- ⟹ 端末側の USB モードは framework が決めており、ホストの刺激では
  再評価されない。**自発的な事象 (端末側の再起動・ボタン) 待ちが正解**。
  ランナーは adb の短い窓 (~10 秒) を 5 秒間隔でポーリングしているので、
  端末が再起動さえすれば自動で fastboot → キュー消化に移行する。

## コンボ自動化の設計 (05:20 検討結果) — 3段階

### 実測で判明している LK のブート判定入力
1. **キー状態** (Vol-Down 等): 実測で fastboot を出せる唯一の確実な入力
   (ユーザーコンボ全成功)。読み取りは PMIC/GPIO レジスタ、**書き込み可能な
   窓 (PMIC 0xFFF34000) に存在する可能性が高い** (0x10F の ABB 書込は実証済み)。
2. **BCB (misc)**: "bootloader" で fastboot (アンロック時の bootonce で実証)。
   書き込みは eMMC ドライバ移植が必要 (重量級、ロードマップ)。
3. **再起動理由レジスタ (PMIC 0x18B 等)**: v1 プローブの実機負結果 +
   adb reboot bootloader が BCB 経由である事実から、**LK は見ていない**
   (reason2 のトレースで最終確認中)。

### 段階設計
- **Stage 1: キー状態レジスタの特定** — キープローブ (実装済み・QEMU PASS・
  キュー投入済み) がキー候補 12 箇所をパス毎に記録。ユーザーのコンボ前後で
  差分を取ると「値が変わるレジスタ = キーの正体」が推測ゼロで確定する。
- **Stage 2: ソフトウェア押下の実証** — 特定したレジスタに「押下中」を書き、
  SMC でリセット → LK が combo を見て fastboot に来れば成功。書込プローブは
  「読んで→書いて→読み戻す」の l1d 方式 (失敗してもトレースが理由を残す)。
  リスクは単一レジスタ書込 + 読み戻し検証で最小化。
- **Stage 3: ループ統合** — fire_probe に「書込→SMCリセット」を足せば、
  プローブ終了 → ソフトウェアコンボ → 次の起動が fastboot → 捕獲器が発射、
  の**完全自走ループ** (人的操作ゼロ) が成立する。
